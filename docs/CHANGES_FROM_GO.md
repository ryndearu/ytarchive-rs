# Changes from the Go source

This port is based on [dreammu/ytarchive](https://github.com/dreammu/ytarchive) at commit `010de44` (2026-10-10), a fork of [Kethsar/ytarchive](https://github.com/Kethsar/ytarchive) at `2110ce2` (2025-06-25). This file lists everything that behaves differently from that source. Anything not listed here is meant to behave the same.

## New features

- **`--sqlite` storage** (idea from [CanOfSocks/livestream_dl](https://github.com/CanOfSocks/livestream_dl)). Fragments are stored in `{name}.f{itag}.sqlite` in the temp directory as soon as they arrive, then exported in order to the `.ts` file at the end. Resuming skips fragments already stored, so a later run only fetches the gaps. A download is resumed in the storage it was started with (database or `.ts`), whatever the flags say when resuming.
- **`--recover-private`: recovery after a stream goes private** (idea from livestream_dl; turns on `--sqlite`). When the stream becomes private or unavailable during the download, Go stopped as soon as a fragment got 403 (the port still does without the flag). With it, the port retries every missing fragment with all the download URLs it has used, in rounds 5 minutes apart, until all are recovered, the URLs expire, or 12 rounds in a row recover nothing. If fragments are still missing and a URL hasn't expired, the temp directory, database, and state files are kept, and running the same command again retries only those fragments (see [Private streams and missing fragments](../README.md#private-streams-and-missing-fragments)). The database is kept up to date during the download (URLs and the newest fragment), so a run that is killed rather than stopped with Ctrl-C can be retried too.
- **`--codec LIST`** picks the video codec order, e.g. `--codec vp9/h264`. Go's `--av1`/`--vp9`/`--h264` still work and can't be combined with `--codec`.
- **The channel monitor remembers recorded streams.** After a stream ends, a channel's `/live` page can keep pointing to it for a while, and Go could download the same stream again. The monitor now skips video IDs it has already recorded in the session.
- **Ended streams whose live download is gone are reported.** Whether an ended stream can still be downloaded is decided from yt-dlp's live (fragmented) URLs, not from the stream's ended or processed status. When none are left, ytarchive prints "Livestream has already ended; its live download no longer exists. Use yt-dlp instead." Go looked only at the watch page's first format and printed "Livestream has been processed" or "is being processed", and an ended stream that YouTube reported as unplayable while processing it got the members-only/cookies hints instead.
## Changed behavior

### Command line

- The help text is generated by clap rather than Go's hand-written page, with the options grouped under headings. All Go flag names except `--potoken` and `--visitor-data` (see below) still work, including single-dash long flags (`-threads`, `-td`, `-dp`, `-fp`).
- `--file-permissions` / `--directory-permissions` (`-fp` / `-dp`) are always read as octal: `755` means `0755`. Go read `755` without a leading zero as decimal.
- `--metadata` without `=` is an error. Go crashed (index out of range).
- `--no-video` together with `--no-audio`, and `--threads 0`, are errors.
- `--potoken` and `--visitor-data` are removed, so passing them is an error. In dreammu they were accepted but never used: the InnerTube request that consumed them (`DownloadWebAPIPlayerResponse`) is never called. Pass PO token settings to yt-dlp with `--ytdlp-opts` instead.
- **The scheduled-stream question is numbered**: `1) wait  2) poll  3) no (default 3):` (the words `wait`/`poll` still work). Go asked `wait/poll/[no]:`. Enter and closed stdin still mean no.
- `--ytdlp-info` asks for the quality while waiting for a scheduled stream, as the default mode does. Go asked only once the stream started.
- **When none of the chosen qualities are available, `best` is used without asking.** Go asked for a quality again, which stalled a download chosen ahead of time (while waiting for a scheduled stream) until someone answered.
- The version shown at startup (unless `-q`) and by `--version` includes the build date, and the commit for non-release builds: `v0.1.0 (2026-11-07)` for releases, `v0.1.0-abc1234 (2026-11-07)` for nightly and other builds.
- Command-line arguments that aren't valid UTF-8 are converted (invalid bytes replaced) instead of rejected.
- **yt-dlp gets a repaired copy of a cookies file it can't read** (the cases are listed under [PO tokens and cookies](../README.md#po-tokens-and-cookies)). Go passed the file as it was, and yt-dlp then failed. A file yt-dlp can read, and a whole JSON export, are still passed as-is.

### Downloading

- The URL is passed to yt-dlp after `--`, so a URL can never be read as a yt-dlp option.
- One yt-dlp run may take 60 seconds before it is stopped and tried again. Go allowed 30, which a slow machine or connection could exceed on every attempt.
- yt-dlp runs with `--encoding utf-8` (and `PYTHONIOENCODING=utf-8`, `PYTHONUTF8=1`), so titles and other text arrive as UTF-8 whatever the console's code page is. `--ytdlp-opts` can still override it.
- **Downloads from a channel URL are pinned to the stream they started on** in `--ytdlp-info` mode too: once `/live` resolves, URL refreshes use the stream's watch URL. Go's yt-dlp mode kept refreshing through `/live` and could switch to a different stream mid-download. `--monitor-channel` still starts each check from `/live`.
- **Waiting on a channel keeps checking `/live` until a stream starts** (with `--monitor-channel`, or a channel URL with `-r`). When `/live` showed a stream marked playable that hadn't started, Go switched to that video's watch URL and kept polling it, so another stream on the channel starting first was missed. The port goes back to `/live` each time. A video URL still waits on that video.
- Requests that return non-2xx statuses are errors (Go's page/thumbnail fetches accepted any response). Error messages omit URL query strings, which contain signatures and your IP; so do the `--debug` lines for a fragment request that failed (Go printed the whole download URL there).
- A connection that stops sending data for 30 seconds is dropped. Go had no limit once a response had started.
- **Failing fragments are retried more slowly when the server is the problem.** Go waited one fragment duration between attempts, whatever the failure. After a connection error, a 5xx, or a 429, the port doubles the wait for each such failure in a row (up to 15 seconds, or the fragment duration if longer), and waits as long as a `Retry-After` header asks (up to 60 seconds). Fragments that aren't there yet (404, empty responses) and 403s are retried at Go's pace.
- **A live fragment that never downloads is skipped** instead of retried until the stream ends. Go started the tries over for as long as the stream was live, so one fragment YouTube never served kept everything after it waiting in memory or fragment files, and nothing more was written to the data file. The port gives up on a fragment once its tries (`--retry-frags`) have run out 4 times while other fragments kept downloading, at least 30 of them since it was first tried; it is reported as skipped, like on an ended stream. When nothing downloads (a connection or server outage), fragments are still retried without limit, and so they are with `--retry-frags 0`.
- **With `--no-frag-files`, the memory used behind a missing fragment is limited.** Go kept every fragment downloaded past a missing one in memory, without limit. Once 256 MiB of a stream (audio and video each) wait that way, the port starts no new fragments until the missing one arrives or is given up on; on a live stream it is then given up on after its tries have run out 4 times. With `--retry-frags 0` it is never given up on, so the download waits for it. Fragment files (the default) and `--sqlite` keep waiting fragments on disk and aren't limited.
- **A failed scheduled URL refresh is tried again after 5 minutes.** Go counted a failed 5-hour refresh as done and waited another 5 hours, by which time the URLs (valid for about 6 hours) had expired, so the download only got new ones after fragments started failing.
- With `--sqlite`, the export to the `.ts` file no longer holds up the other stream's download while it runs.
- A temp directory named in a saved state file is only reused if it still exists.
- `--separate-audio` only makes the extra audio file when both audio and video were downloaded. Go also made a duplicate for audio-only downloads.

### Files and cleanup

- Only temp directories named `{video_id}__*` (the ones ytarchive creates) are ever deleted. Go deleted whatever directory a state file named, so a corrupted state file could point it at any directory.
- The final file's name (`name.mp4`, or `name-1.mp4` … if taken) is picked again right before muxing, and the `.ffmpeg.txt` command is updated to match. Go picked it before the download started, so a file created under that name during the download made ffmpeg fail.
- When `name.mp4` and `name-1.mp4` to `name-10.mp4` all exist, ytarchive says so and doesn't run ffmpeg; the `.ts` files are kept. Go ran ffmpeg, which refused to overwrite, and reported only its exit code.- The `publish_date` template value is always `YYYYMMDD`. Go kept the raw value, which for newer pages includes a time and offset.

### Output and signals

- The progress line is written to stderr (Go used stdout).
- After the first Ctrl-C (which stops the download and leads to the merge/save questions), a second one exits immediately, matching the effect of Go's `signal.Reset`.

## Platform support

Windows, Linux, and macOS are supported. Go built for more targets but only supported Linux and Windows builds.

- **TLS uses rustls** (with the `ring` crypto library) on every platform instead of Go's built-in TLS. Certificates come from the operating system's store. No OpenSSL is needed, so the Linux release builds are static and run on any distribution.
- **Windows console handling** (port of `util_windows.go`): the system is kept awake while ytarchive runs, ANSI colors are enabled (Go used go-colorable), and QuickEdit mode is turned off (see the bug fix below) and restored on exit. All of it goes through safe wrapper crates; the port contains no `unsafe` code.
- **`--windows-filenames` / `--no-windows-filenames`** (new). With Windows names (default on Windows), forbidden and control characters, reserved names (`CON`, `NUL`, `COM1`, …, also with an extension), and trailing dots and spaces are replaced in the file name and in every folder created from the output template, and the title is shortened so every path ytarchive writes (final and temporary) fits in Windows' 260-character MAX_PATH; `--no-path-limit` (new) turns the shortening off. Without them (default elsewhere), only path separators and NUL are replaced. Go always replaced `<>:"/\|?*`, only in the file name, and nothing else.
- **x64 and arm64 builds for every platform.** Go's releases had no Windows arm64 build.
- **The `.ffmpeg.txt` command uses the platform's quoting**: POSIX shell quoting on Linux/macOS, Windows command-line quoting on Windows. Go always used POSIX quoting.
- **`ffmpeg`/`yt-dlp` next to the executable are found**, in addition to `PATH` (handy on Windows). Go also allowed binaries in the current directory.

## Go bugs fixed during the port

1. **Filename blacklist was never applied.** `FormatFilename` blanked `description` and then immediately overwrote it with the real value, so `%(description)s` in a template inserted the whole description.
2. **Template expansion could loop forever.** `FormatPythonMapString` re-scanned substituted values, so a title containing its own placeholder (e.g. `%(title)s`) never finished. Substitution is now single-pass.
3. **Long-name truncation was too small for repeated titles.** When a template used `%(title)s` more than once, only one copy's worth was removed. Every copy is now shortened enough to fit.
4. **Session cookies were discarded.** Cookies with expiry `0` were given a 1970 expiry date, which made Go's cookie jar drop them.
5. **`--live-from` 7-day check compared different units.** It compared a fragment count against a number of seconds.
6. **Missing start timestamps crashed.** Slicing an empty timestamp string panicked; malformed googlevideo `id` parameters did too.
7. **"Try N more times" never retried.** `ContinueFragmentDownload` promised extra attempts for fragments behind the head but didn't reset the try counter, so the download loop exited immediately and the fragment was dropped.
8. **One bad fragment ended the whole download.** On an ended stream, a fragment well behind the head that failed permanently ended the download, silently dropping everything after it. The port skips that one fragment, keeps going, and lists the missing sequence numbers at the end.
9. **Slower workers gave up early.** When one worker reached the last sequence it marked the stream finished, and other workers abandoned the fragments they were still retrying. Running out of sequence numbers now only stops that worker.
10. **Resuming with a missing data file produced a broken file.** Go marked the download as resumed and continued writing into a new empty file. It now starts over.
11. **MP4 box scanning could hang and was incomplete.** A zero-length box made `GetAtoms` loop forever, and only the first 8 KiB of each fragment was scanned for `sidx`/`ftyp`.
12. **The ffmpeg command could reference a missing thumbnail.** The arguments were built before the thumbnail download, so a failed download broke the merge. They are now built afterwards.
13. **The audio/video mismatch warning never fired.** The fragment counts it compared were never incremented.
14. **Disabling QuickEdit never worked.** Go cleared `ENABLE_QUICK_EDIT_MODE` without the `ENABLE_EXTENDED_FLAGS` bit Windows requires, so a click in the console could still pause the download. The port sets both, and restores the original console mode on exit.
15. **Page downloads failed with HTTP/2 errors** (port-specific, found while testing). With a Firefox user agent YouTube sends ~20 KB of response headers, above the HTTP library's 16 KB default. The limit is raised.
16. **`--file-permissions` skipped the final file.** Go applied it only to files it wrote itself (thumbnail, description, mux file, state and fragment files); the muxed file and the `--separate-audio` file kept ffmpeg's default mode. The port sets the mode on both after muxing.
17. **Repeating a flag was an error** (port-specific, found while testing the nightly). v0.1.0 rejected a flag given twice, e.g. `--ytdlp-opts … --ytdlp-opts …` or `-o a -o b`. As with Go's flag package, the last value now wins; `--metadata` still collects every value.
18. **Ctrl-Break didn't stop the download on Windows** (port-specific). Go's `os.Interrupt` catches both Ctrl-C and Ctrl-Break; v0.1.0 caught only Ctrl-C, so Ctrl-Break ended the program without merging or saving. Both now stop the download (and exit from a prompt) the same way.
19. **A download whose file couldn't be created was still "finished" and muxed.** When a stream's data file or database couldn't be opened (e.g. a name Windows rejects under `--no-windows-filenames`), Go logged the error, then printed "Download Finished" and ran ffmpeg on the missing file, which failed with code -22. The port doesn't merge and exits with 1: if nothing was downloaded it removes the temp folder and state files, and if an earlier run's data is there (a resume) it leaves everything to resume once the cause is fixed.
20. **A crash while saving the state could lose the whole download.** Go rewrote the `.state` file in place after every fragment, so a crash or power loss mid-write left an unreadable file; the next run then started from the beginning and overwrote the data already downloaded. The port writes the state to a temporary file and renames it over the old one, and a data file that can't be resumed (its state is missing, unreadable, or doesn't match) is kept as `{name}.f{itag}.ts.old` instead of being overwritten. That applies when the temp folder is reused, i.e. the other stream's state was still good or the file is shorter than its state says; when no state can be read, the run uses a new temp folder and the old one is left untouched. The cleanup after merging leaves a `.old` file and its temp folder in place and says so.

## Not ported

These parts of Go were unreachable, unused, or only documented, so they were left out:

- **InnerTube player request** (`DownloadWebAPIPlayerResponse`), the `ytcfg` scraping that fed it, and **SAPISIDHASH** authentication. None of them are called in dreammu.
- **DASH manifest parsing** (`GetUrlsFromManifest`, `MPD` types): never called in dreammu, since yt-dlp provides the URLs.
- **UMP parsing** (`yt_ump.go`): never called.
- **Slow-fragment URL refresh**: Go counted slow fragments, but the refresh call is commented out.
- **`--info-only`**: listed in dreammu's README, but neither Go codebase implements it.
