# Changes from the Go source

This port is based on [dreammu/ytarchive](https://github.com/dreammu/ytarchive) at commit `010de44` (2026-10-10), a fork of [Kethsar/ytarchive](https://github.com/Kethsar/ytarchive) at `2110ce2` (2025-06-25). Everything that behaves differently is listed here; anything else is meant to behave the same.

## New features

- **`--sqlite`** (idea from [CanOfSocks/livestream_dl](https://github.com/CanOfSocks/livestream_dl)): fragments are stored in `{name}.f{itag}.sqlite` in the temp directory as they arrive and exported in order to the `.ts` file at the end. Resuming fetches only the missing ones. A download is resumed in the storage it was started with, whatever the flags say.
- **`--recover-private`** (idea from livestream_dl; turns on `--sqlite`): once a stream went private, Go stopped at the first 403 (the port still does without the flag). With it, missing fragments are retried with the URLs already used, and a later run can retry what is still missing; see [Private streams and missing fragments](../README.md#private-streams-and-missing-fragments).
- **`--codec LIST`**: the video codec order, e.g. `--codec vp9/h264`. Go's `--av1`/`--vp9`/`--h264` still work but can't be combined with it.
- **The channel monitor skips streams it already recorded.** `/live` can keep pointing to an ended stream, and Go could download it again. Already-recorded video IDs are skipped when scanning `/streams` (allowing simultaneous streams on the same channel to be picked up) and before invoking `yt-dlp`. Streams whose download exited with an error are retried once and marked done after 2 failed attempts so permanent failures do not loop forever.
- **An ended stream whose live download is gone is reported**: "Livestream has already ended; its live download no longer exists. Use yt-dlp instead." This is decided from yt-dlp's live URLs. Go looked only at the watch page's first format, printed "has been processed" or "is being processed", and could show the members-only hints instead.

## Changed behavior

### Command line

- The help text is generated by clap, grouped under headings. All Go flag names still work, including single-dash long flags (`-threads`, `-td`, `-dp`, `-fp`), except `--potoken` and `--visitor-data`: dreammu accepted but never used them, so they are removed. Pass PO token settings with `--ytdlp-opts`.
- `--file-permissions` / `--directory-permissions` are always octal (`755` means `0755`). Go read `755` as decimal.
- These are errors: `--metadata` without `=` (Go crashed), `--no-video` with `--no-audio`, `--threads 0`, and unclosed quotes in `--ytdlp-opts`.
- `--ytdlp-opts` parses single and double quotes (preserving Windows backslashes outside quote escapes); `--live-from` syntax and the 7-day seek bound are validated at startup; and `--metadata` templates referencing unknown keys warn at startup while keeping the literal fallback.
- The scheduled-stream question is numbered: `1) wait  2) poll  3) no (default 3):` (`wait`/`poll` still work; Enter and closed stdin mean no). Go asked `wait/poll/[no]:`.
- `--ytdlp-info` asks for the quality while waiting for a scheduled stream. Go asked once the stream started.
- When none of the chosen qualities are available, `best` is used. Go asked again, which stalled an unattended download.
- The version includes the build date, and the commit for non-release builds: `v0.1.0 (2026-11-07)`, `v0.1.0+abc1234 (2026-11-07)`.
- Arguments that aren't valid UTF-8 are converted instead of rejected.
- yt-dlp gets a repaired copy (in the temp folder, deleted on exit) of a cookies file it can't read: not UTF-8, no `# Netscape HTTP Cookie File` header, a second column that doesn't match the domain's leading `.`, or a stray line starting like JSON. Go passed the file as it was, and yt-dlp failed.
- `--members-only` warns and is ignored for video URLs (Go skipped fetching the watch page and failed), and warns on channel URLs when `--cookies` is not given.
- `--proxy` accepts `socks5h://` (remote DNS resolution) in addition to `http`, `https`, and `socks5` (Go rejected `socks5h`).

### Downloading

- The URL is passed to yt-dlp after `--`, so it can't be read as an option.
- A yt-dlp run may take 60 seconds (Go: 30) before it is stopped and tried again.
- yt-dlp runs with `--encoding utf-8` (and `PYTHONIOENCODING=utf-8`, `PYTHONUTF8=1`), so text arrives as UTF-8 whatever the console's code page is. `--ytdlp-opts` can override it.
- `-4` and `-6` are forwarded to yt-dlp (`--force-ipv4` / `--force-ipv6`), so extracted URLs match the IP family used for downloading.
- In `--ytdlp-info` mode, exact `format_id` entries are preferred over suffixed variants (such as `140` over `140-drc`), keeping the last (highest-preference) suffixed variant when no exact ID exists, and `target_duration` prefers adaptive formats over non-adaptive ones.
- The `X-Head-Seqnum` HEAD probe sends the fragment's `Referer` header and retries up to 3 times (1 second apart) on missing headers or request errors. Go sent a single HEAD request without `Referer`.
- `--ytdlp-info` supports waiting on a channel URL with `-r` (polling once per interval without multi-attempt retries, aborting if `yt-dlp` cannot be started and warning on unexpected errors), rejects negative `--live-from` durations on upcoming streams, and exits cleanly if `is_upcoming` is reported mid-download. Go failed immediately on channels with no active stream and did not check those conditions in `--ytdlp-info` mode.
- **Scheduled-stream waits re-check the wall clock every 60 seconds** in both default and `--ytdlp-info` modes so waking from system sleep or suspend does not delay the start. Go slept the full interval in one call.
- Netscape cookie parsing accepts fractional expiry timestamps instead of treating them as session cookies.
- **A download from a channel URL stays on the stream it started on** in `--ytdlp-info` mode too: URL refreshes use the stream's watch URL. Go kept refreshing through `/live` and could switch streams mid-download.
- **Waiting on a channel keeps checking `/live`** (`--monitor-channel`, or a channel URL with `-r`). When `/live` showed a playable stream that hadn't started, Go switched to its watch URL and missed another stream that started first.
- Non-2xx responses are errors (Go's page and thumbnail fetches accepted any). Error, `--debug`, and `--trace` messages omit URL query strings (which hold signatures and your IP) and proxy credentials.
- A connection that sends nothing for 30 seconds is dropped. Go had no limit.
- **Retries slow down when the server is the problem.** After a connection error, a 5xx, or a 429, the wait doubles for each such failure in a row (up to 15 seconds, or the fragment duration if longer), and `Retry-After` is followed up to 60 seconds. Go always waited one fragment duration; the port still does for 404s, empty responses, and 403s.
- **A live fragment that never downloads is skipped.** Go retried it for as long as the stream was live, holding back everything after it. The port gives up once its tries (`--retry-frags`) have run out 4 times while at least 30 other fragments downloaded. During an outage, and with `--retry-frags 0`, fragments are retried without limit.
- **With `--no-frag-files`, the memory behind a missing fragment is limited.** Once 256 MiB of a stream wait behind it, no new fragments start until it arrives or is given up on (after its tries have run out 4 times; never with `--retry-frags 0`). Go had no limit.
- **Single-threaded downloads (`--threads 1`) skip temporary fragment files**, since fragments arrive in sequence order.
- **Failing fragments don't keep a `--capture-duration` download from finishing.** After the capture's last fragment has started, each failing one is given up on once its tries have run out 4 times, if anything else downloaded since it was first tried. An outage during the last fragments that lasts that long loses them. `--capture-duration` also counts from `start_frag` when resuming `.ts` downloads, matching `--sqlite`.
- **A failed scheduled URL refresh is tried again after 5 minutes.** Go waited another 5 hours, longer than the URLs last (about 6 hours).
- **A URL refreshed after 403 on an ended stream is actually tried.** After exhausting tries on a 403, a refreshed URL resets retries for another round (up to 2 refreshes per fragment) instead of immediately failing on Go's stale 403 flag, and `is_403` is cleared on non-403 failures.
- **`--retry-frags 0` still triggers URL refreshes** every 10 failed attempts on a fragment while continuing to retry indefinitely. Go disabled retry-triggered URL refreshes when `--retry-frags` was 0.
- **Transient network errors during a refresh keep the stream refreshable.** A brief outage while refreshing URLs no longer permanently marks a live stream unavailable.
- **Failed URL refreshes update the cooldown timestamp after extraction finishes** (and skip extraction once marked unavailable), preventing queued workers from re-running slow extractions back-to-back.
- **Mid-download `ERROR`, `UNPLAYABLE`, or unknown (such as `LOGIN_REQUIRED`) playability statuses consistently mark the stream both not-live and unavailable.** Go left `Unavailable` unset on `ERROR`/unknown statuses and `Live` set on `UNPLAYABLE`.
- SQLite inserts (with batched `head`/URL metadata updates), queries, and exports, saving the resume state, and moving finished files to another filesystem run off the async runtime thread so they no longer hold up the download. The state file can be a few fragments behind the data; resuming cuts the data file back to it. SQLite exports are skipped after a storage error and deferred until after Ctrl-C prompts so discarding a cancelled download does not write a `.ts` file first.
- A temp directory named in a state file is reused only if it still exists.
- `--separate-audio` makes the extra file only when both audio and video were downloaded (Go also duplicated audio-only downloads), and writes both commands to `.ffmpeg.txt` if muxing the separate audio fails (Go wrote only the main command).

### Files and cleanup

- Only temp directories named `{video_id}__*` are ever deleted. Go deleted whatever directory a state file named.
- Metadata values equal to `..` are sanitized to `__`, and title truncation reserves room for leading `-` or Windows reserved-name `_` prefixes added afterward as well as fragment/SQLite suffixes (`.f{itag}.frag{seq}.ts`, `.f{itag}.sqlite-wal`) within the 255-byte component limit.
- Repaired yt-dlp cookies files use randomized temporary filenames (`0600` on Unix), are removed via an exit guard, and stale copies older than a day are cleaned up when creating a new copy (skipping any copy locked by a running `ytarchive` process).
- The final file's name (`name.mp4`, `name-1.mp4`, …) is picked right before muxing, and the `.ffmpeg.txt` command is updated to match. Go picked it before the download, so a file that appeared meanwhile made ffmpeg fail.
- When `name.mp4` to `name-10.mp4` all exist, ffmpeg isn't run and the `.ts` files are kept. Go ran ffmpeg and reported only its exit code.
- Resume state files are deleted only after moving temporary files succeeds, and partial cross-filesystem copies are deleted on failure.
- Saving created files on cancel (`--save`) also moves the `.ffmpeg.txt` command file to the output directory instead of deleting it with the temporary directory.
- Failures when applying `--file-permissions` or `--directory-permissions` (for example on filesystems without Unix permissions such as exFAT, FAT32, or SMB) are logged at debug level instead of failing or deleting written files.
- `publish_date` is always `YYYYMMDD`. Go kept the raw value, which can include a time and offset.

### Output and signals

- The progress line is written to stderr (Go: stdout).
- ANSI color/clear escapes (including `\x1b[K` on general logs) and `\r` status rewrites are omitted when stderr is not a terminal, and colors respect `NO_COLOR`.
- `ffmpeg` inherits stderr directly (or silences it under `--quiet`) rather than reading chunks through lossy UTF-8 decoding.
- A second Ctrl-C exits immediately, like Go's `signal.Reset`.
- On Linux and macOS, `SIGTERM` stops the download gracefully without interactive prompts, leaves the temporary folder and state files intact for resuming, and exits with 143 (a second signal exits immediately). Interactive prompts coordinate with the main signal listener instead of registering a second handler.
- On Ctrl-C with closed stdin while waiting on an interactive cancel prompt, temporary files and resume state are left intact for resuming instead of deleting the download (Go treated EOF as "no" to every prompt).
- Interrupting cancels in-flight HTTP requests and kills running `yt-dlp` subprocesses right away instead of waiting for timeouts.

## Platform support

Windows, Linux, and macOS are supported, each as x64 and arm64. Go built for more targets but supported only Linux and Windows, and had no Windows arm64 build.

- **TLS is rustls** (with `ring`) and the operating system's certificate store. No OpenSSL is needed, so the Linux builds are static.
- **Windows console** (port of `util_windows.go`): the system is kept awake, ANSI colors are enabled, and QuickEdit mode is turned off and restored on exit, all through safe wrapper crates (no `unsafe`).
- **`--windows-filenames` / `--no-windows-filenames` / `--no-path-limit`** (new; see [File names](../README.md#file-names)). Go always replaced `<>:"/\|?*`, only in the file name, and didn't keep paths within MAX_PATH.
- **The `.ffmpeg.txt` command uses the platform's quoting.** Go always used POSIX quoting.
- **`ffmpeg`/`yt-dlp` next to the executable are found**, besides `PATH`, and executed by resolved path on every OS (including Linux and macOS). Go also looked in the current directory.

## Go bugs fixed during the port

1. **Filename blacklist was never applied.** `FormatFilename` blanked `description` and then immediately overwrote it with the real value, so `%(description)s` in a template inserted the whole description.
2. **Template expansion could loop forever.** `FormatPythonMapString` re-scanned substituted values, so a title containing its own placeholder (e.g. `%(title)s`) never finished. Substitution is now single-pass.
3. **Long-name truncation was too small for repeated titles.** When a template used `%(title)s` more than once, only one copy's worth was removed. Every copy is now shortened enough to fit.
4. **Session cookies were discarded.** Cookies with expiry `0` were given a 1970 expiry date, which made Go's cookie jar drop them.
5. **`--live-from` 7-day check compared different units.** It compared a fragment count against a number of seconds.
6. **Missing start timestamps crashed.** Slicing an empty timestamp string panicked; malformed googlevideo `id` parameters did too.
7. **"Try N more times" never retried.** `ContinueFragmentDownload` promised extra attempts for fragments behind the head but didn't reset the try counter, so the download loop exited immediately and the fragment was dropped.
8. **One bad fragment ended the whole download.** On an ended stream, a fragment well behind the head that failed permanently ended the download, silently dropping everything after it. The port skips that one fragment, keeps going, and lists the missing sequence numbers at the end. Skipped counts are recorded in the resume state (`Skipped`, omitted when zero) so resuming a `.ts` download does not re-fetch and duplicate earlier fragments.
9. **Slower workers gave up early.** When one worker reached the last sequence or hit a near-head failure on an ended stream, it marked the stream finished and other workers abandoned the fragments they were still retrying. Running out of sequence numbers or hitting a near-head end now only caps further sequences (judged against the stream's latest known head) so earlier fragments finish retrying.
10. **Resuming with a missing data file produced a broken file.** Go marked the download as resumed and continued writing into a new empty file. It now starts over. The progress line counts what the storage holds once it is opened, not what the state file says; v1.0.0 counted the state file's fragments and bytes even when the download started over, so the count went past "Max Fragments".
11. **MP4 box scanning could hang and was incomplete.** A zero-length box made `GetAtoms` loop forever, and only the first 8 KiB of each fragment was scanned for `sidx`/`ftyp`.
12. **The ffmpeg command could reference a missing thumbnail.** The arguments were built before the thumbnail download, so a failed download broke the merge. They are now built afterwards.
13. **The audio/video mismatch warning never fired.** The fragment counts it compared were never incremented.
14. **Disabling QuickEdit never worked.** Go cleared `ENABLE_QUICK_EDIT_MODE` without the `ENABLE_EXTENDED_FLAGS` bit Windows requires, so a click in the console could still pause the download. The port sets both, and restores the original console mode on exit.
15. **`--file-permissions` skipped the final file.** Go applied it only to files it wrote itself (thumbnail, description, mux file, state and fragment files); the muxed file and the `--separate-audio` file kept ffmpeg's default mode. The port sets the mode on both after muxing.
16. **A download whose file couldn't be created was still "finished" and muxed.** Go logged the error, printed "Download Finished", and ran ffmpeg on the missing file (e.g. a name Windows rejects under `--no-windows-filenames`). The port doesn't merge and exits with 1, as it does when storing fails later (full disk, failed temp fragment write, failed `--sqlite` export): a fresh download's temp folder and state files are removed, and a resumed one is left to resume once the cause is fixed.
17. **A crash while saving the state could lose the whole download.** Go rewrote the `.state` file in place, so a crash mid-write left it unreadable, and the next run started over and overwrote the data. The port writes it to a temporary file and renames it, and keeps a data file that can't be resumed as `{name}.f{itag}.ts.old` instead of overwriting it. The state isn't synced before the rename (each save was about 20 times slower), so this covers a program crash, not a power loss.

## Not ported

These parts of Go were unreachable, unused, or only documented, so they were left out:

- **InnerTube player request** (`DownloadWebAPIPlayerResponse`), the `ytcfg` scraping that fed it, and **SAPISIDHASH** authentication. None of them are called in dreammu.
- **DASH manifest parsing** (`GetUrlsFromManifest`, `MPD` types): never called in dreammu, since yt-dlp provides the URLs.
- **UMP parsing** (`yt_ump.go`): never called.
- **Slow-fragment URL refresh**: Go counted slow fragments, but the refresh call is commented out.
- **`--info-only`**: listed in dreammu's README, but neither Go codebase implements it.
